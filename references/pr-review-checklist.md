# PR 审查 Checklist

快速参考：审 PR 时逐项过一遍。配合 `github-pr-review` skill 使用。

## 必查项

### 🔴 必须改（阻塞合并）

- [ ] 有没有把密钥/凭证写进代码？（grep `password`、`secret`、`token`、`api_key`）
- [ ] `subprocess.run(..., shell=True)` 有没有拼接外部输入？
- [ ] 路径操作有没有用 `os.path.join` 而不是字符串拼接？
- [ ] SQL 查询有没有参数化？
- [ ] 新接口有没有做输入校验？
- [ ] 错误处理有没有吞异常？（`except: pass`）

### 🟡 建议改（非阻塞）

- [ ] 命名是否清晰？（`data1`、`foo`、`temp` 这类）
- [ ] 函数是不是太长？（>50 行考虑拆）
- [ ] 注释是不是在解释「为什么」而不是「做什么」？
- [ ] 有没有死代码？（注释掉的代码、没用的 import）
- [ ] 测试有没有覆盖新逻辑？

### 🟢 写得好的地方

- [ ] 错误信息对用户友好
- [ ] 边界条件处理（空 list、None、空字符串）
- [ ] 命名和现有代码库一致
- [ ] 有文档字符串/注释

## 大 PR 策略（>500 行）

1. 先按模块分组（API / 业务逻辑 / 测试 / 配置）
2. 每组挑 1-2 个重点文件细看
3. 其他文件只扫一眼 diff 有没有明显问题
4. 不要逐行纠缠小问题

## 新测试 PR

- 断言真的断言了行为吗？（`assert True` 这种假断言）
- 有没有 mock 过度到没意义？
- 边界条件有没有覆盖？
